## 1. Тема и целевая аудитория

### Тема
Высоконагруженная платформа визуального поиска и сохранения идей (Pinterest). Ближайший аналог - Pinterest.

Pinterest представляет собой визуальную поисковую платформу, которая позволяет пользователям искать, организовывать и сохранять идеи в различных тематических областях. Сервис сочетает в себе функции социальной сети, визуального поиска и системы закладок. Пользователи создают доски, на которых сохраняют пины - изображения, видео или ссылки на внешние ресурсы.

### Целевая аудитория
Основная аудитория сервиса состоит из следующих групп:
- **Пользователи** - люди, которые ищут вдохновение, сохраняют идеи, создают доски и планируют различные активности;
- **Бизнес-пользователи и бренды** - компании, которые публикуют контент, продвигают продукты и взаимодействуют с аудиторией через рекламные инструменты.

По итогам IV квартала 2025 года глобальная MAU платформы достигла 619 млн (+12% г/г) [[1]](https://www.sec.gov/Archives/edgar/data/1506293/000150629326000019/q4-25xpressrelease.htm), по итогам II квартала 2026 года - 640 млн MAU (+11% г/г) [[4]](https://www.sec.gov/Archives/edgar/data/0001506293/000150629326000102/q2-26xpressrelease.htm).

География - глобальная. Q4'25: США и Канада - 105 млн MAU, Европа - 158 млн MAU, остальной мир - 356 млн MAU [[1]](https://www.sec.gov/Archives/edgar/data/1506293/000150629326000019/q4-25xpressrelease.htm), [[6]](https://sproutsocial.com/insights/pinterest-statistics/).

Портрет аудитории:
- Поколение зумеров стало крупнейшим поколенческим сегментом в 2025 году [[8]](https://www.sec.gov/Archives/edgar/data/1506293/000150629325000195/q2-25xpressrelease.htm);
- Основная выручка и монетизация - США и Канада [[1]](https://www.sec.gov/Archives/edgar/data/1506293/000150629326000019/q4-25xpressrelease.htm).

### Функционал MVP
1. Регистрация и авторизация пользователей;
2. Создание, редактирование и удаление пинов;
3. Создание и управление досками;
4. Сохранение пина на доску;
5. Визуальный и текстовый поиск;
6. Просмотр ленты рекомендаций;
7. Лайк пинов.

### Ключевые продуктовые решения
- Визуальная поисковая платформа, а не социальная сеть;
- Контент организован по доскам и пинам;
- Персонализация на основе сохранений и поведения;
- Визуальный поиск по загруженному изображению;
- Мобильный приоритет.

## 4. Локальная балансировка нагрузки

### 4.1. Схема балансировки нагрузки и механизмы резервирования

#### 4.1.1. Уровни балансировки внутри ДЦ

Внутри ДЦ трафик проходит четыре уровня балансировки. ДЦ делится на две зоны доступности (A и B) - группы стоек с независимым питанием и сетью, они служат доменами отказа.

Резервирование построено по модели **перелива нагрузки (spillover)**: зона не держит запас на всю нагрузку соседней зоны. Каждая зона рассчитана на свою половину нагрузки ДЦ и один запасной узел. Когда загрузка зоны или ДЦ достигает порога **80 %**, избыток начинает распределяться в другую зону или в соседние регионы, у которых есть свободная ёмкость.

```mermaid
flowchart TB
  U["Клиент: браузер, мобильное приложение"]
  GD["GeoDNS / Global Accelerator: веса регионов"]
  CDN["CDN: cache hit 90% с edge"]
  CTRL["Контроллер перелива: порог 80 %, возврат ниже 70 %"]
  NB["Соседние регионы: свободная ёмкость до 80 %"]

  U -->|"API"| GD
  U -->|"медиа"| CDN

  subgraph DC["Региональный ДЦ"]
    subgraph ZA["Зона A"]
      L4A["L4, узел 1"]
      L7A["NGINX Ingress: ⌈N/2⌉+1 узлов"]
    end
    subgraph ZB["Зона B"]
      L4B["L4, узел 2"]
      L7B["NGINX Ingress: ⌈N/2⌉+1 узлов"]
    end
    SVC["Envoy-sidecar + поды сервисов в обеих зонах"]
    PRX["ProxySQL * 2, N*2"]
    DB[("MySQL: primary + реплики по шардам")]
  end

  GD --> L4A
  GD --> L4B
  CDN -->|"cache miss 10%"| L4A
  CDN -->|"cache miss 10%"| L4B
  L4A --> L7A
  L4A --> L7B
  L4B --> L7A
  L4B --> L7B
  L7A --> SVC
  L7B --> SVC
  SVC --> PRX
  PRX --> DB
  L7A -.->|"загрузка"| CTRL
  L7B -.->|"загрузка"| CTRL
  CTRL -.->|"веса регионов"| GD
  CTRL -.->|"веса origin"| CDN
  CDN -.->|"перелив промахов при загрузке ДЦ > 80 %"| NB
```

Выбранные решения:
- **Медиа** (96% пинов - изображения) почти целиком обслуживает CDN;
- **Envoy-sidecar** нужен, потому что HTTP/2 держит одно соединение;
- **СУБД:** MySQL с шардированием [[10]](https://medium.com/pinterest-engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f);
- **L4** в AWS - управляемый NLB, моделируется как пара независимых узлов;
- **Перелив между регионами** выполняется для промахов CDN: это медиатрафик без состояния (120 из 134,85 Гбит/с), соседний регион отдаёт файл из S3 так же, как домашний. API остаётся в домашнем регионе, где лежат данные пользователя.

#### 4.1.2. Алгоритмы балансировки на каждом уровне

| Участок | Алгоритм | Причина выбора | Резервирование |
| --- | --- | --- | --- |
| Маршрутизаторы - L4 | ECMP по хешу потока | равномерно, поток не рвётся [[17]](https://research.google/pubs/pub44824/) | оба L4 активны, при отказе - перераспределение |
| NGINX | consistent hashing + DSR | соединение на своём узле | health-check исключает недоступный; запасной узел в каждой зоне |
| сервис | random two least_conn [[18]](https://nginx.org/en/docs/http/ngx_http_upstream_module.html) | учитывает активные соединения | readiness-проба, graceful drain |
| Envoy - реплика | least request + zone-aware routing | HTTP/2 - одно соединение, балансируем запросы; запрос остаётся в своей зоне | outlier detection, повтор идемпотентных; при падении доступной ёмкости зоны ниже 80 % (overprovisioning factor 1,25) избыток уходит во вторую зону [[33]](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/load_balancing/priority) |
| ProxySQL - MySQL | read в реплику, write в primary | у шарда один primary | при отказе primary - реплика повышается |
| ДЦ - соседние регионы | перелив по порогу: веса регионов в Global Accelerator (traffic dial) [[34]](https://docs.aws.amazon.com/global-accelerator/latest/dg/about-endpoint-groups-traffic-dial.html) и веса origin для CDN в Route 53 [[35]](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html) | при загрузке ДЦ от 80 % избыток уходит в регионы со свободной ёмкостью пропорционально их запасу | регион с отказом зоны не перегружается; возврат трафика при загрузке ниже 70 % |

#### 4.1.3. Формулы резервирования

| Формула | Что означает | От чего защищает |
| --- | --- | --- |
| **N+1** | N узлов под пик + 1 запасной | Отказ **одного** узла |
| **N*2** | Два независимых комплекта, каждый держит весь пик (active-active) | Отказ **целой зоны** |
| **2 * (⌈N/2⌉ + 1) + перелив** | В каждой из двух зон половина рабочих узлов и 1 запасной; при отказе зоны оставшаяся работает до порога 80 %, избыток переливается в соседние регионы | Отказ **узла** - запасным узлом зоны; отказ **зоны** - общим запасом всех регионов |

**Применение по уровням:**
- **L4** - N*2 (N = 1, управляемый NLB);
- **L7 (NGINX)** - 2 * (⌈N/2⌉ + 1) + перелив;
- **Envoy** - поды поровну в двух зонах, zone-aware routing с переливом во вторую зону; HPA добавляет поды при загрузке CPU выше 80 %;
- **ProxySQL** - N*2: N = 1, путь к локальной БД нельзя перелить в другой регион, а удвоение стоит один узел.

**Порог и гистерезис перелива:**
- **рабочая точка - 70 %** производительности узла: по ней считается число рабочих узлов N;
- **порог перелива - 80 %**: выше него избыток уходит во вторую зону (Envoy) или в соседние регионы (веса Global Accelerator и origin CDN);
- **возврат - ниже 70 %**: разница 10 п.п. не даёт трафику «качаться» между регионами;
- **предел - 100 %** измеренной производительности: запас 20 % между порогом и пределом покрывает время реакции контроллера (десятки секунд).

**Почему перелив, а не 2(N+1).** В схеме 2(N+1) каждая зона держит весь пик ДЦ: в штатном режиме половина узлов простаивает, и при этом заранее неизвестно, сколько нагрузки придёт при отказе. При переливе резерв общий для всех регионов: регионы пикуют в разное время (часовые пояса), а одновременно отказывает не больше одной зоны. Свободной ёмкости трёх регионов до порога 80 % хватает, чтобы принять избыток одной зоны (проверка в п. 4.2.4). Узлов NGINX требуется 30 вместо 52.

#### 4.2.3. Расчёт по ограничителям SSL Termination и сети

- N_RPS = ⌈ API_RPS / 132 800 ⌉

- N_TLS = ⌈ новых TLS-соединений / 38 414 ⌉

- N_net = ⌈ исходящий трафик ДЦ / 6,16 ⌉

- N = max(N_RPS, N_TLS, N_net) - рабочих узлов ДЦ на рабочей точке 0,7

- n_zone = ⌈ N / 2 ⌉ + 1 - узлов в зоне: половина рабочих + запасной

- L7 = 2 * n_zone

- L4 = 2

| ДЦ | N_RPS | N_TLS штатный | N_TLS худший | N_net | **N** | ⌈N/2⌉+1 | **2 * (⌈N/2⌉+1)** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| US&Canada | 1 | 1 | 2 | 4 | **4** | 3 | **6** |
| Европа | 1 | 1 | 2 | 6 | **6** | 4 | **8** |
| ROW | 2 | 1 | 4 | 13 | **13** | 8 | **16** |
| **Всего** | 4 | 3 | 8 | 23 | **23** | 15 | **30** |


#### 4.2.4. Проверка отказоустойчивости и перелив нагрузки

Определяющий ограничитель - сеть, поэтому проверка ведётся в Гбит/с. Ёмкость на пороге = число узлов * 7,04 Гбит/с, загрузка - в процентах от измеренной производительности узла 8,80 Гбит/с.

| Показатель | US&Canada | Европа | ROW |
| --- | ---: | ---: | ---: |
| Трафик ДЦ, Гбит/с | 22,93 | 34,39 | 77,54 |
| Узлов NGINX | 6 | 8 | 16 |
| Ёмкость на пороге 80 %, Гбит/с | 42,24 | 56,32 | 112,64 |
| Свободно до порога, Гбит/с | 19,31 | 21,93 | 35,10 |

| Состояние | US&Canada | Европа | ROW |
| --- | ---: | ---: | ---: |
| Штатно | 43% | 49% | 55% |
| Отказ узла | 65% | 65% | 63% |
| Отказ зоны | 80%, перелив 1,81 Гбит/с | 80%, перелив 6,23 Гбит/с | 80%, перелив 21,22 Гбит/с |
| Отказ зоны + узла | 80%, перелив 8,85 Гбит/с | 80%, перелив 13,27 Гбит/с | 80%, перелив 28,26 Гбит/с |

«Отказ узла» - загрузка зоны, в которой отказал узел: её половина трафика ложится на оставшиеся узлы зоны, перелив не нужен. При отказе зоны оставшаяся зона работает на пороге 80 %, избыток уходит в соседние регионы пропорционально их свободной ёмкости.

```text
Отказ зоны ROW:
  оставшаяся зона:  8 * 7,04 = 56,32 Гбит/с на пороге
  перелив:          77,54 - 56,32 = 21,22 Гбит/с
  приёмники:        US&Canada 19,31 + Европа 21,93 = 41,24 Гбит/с свободно
  в US&Canada:      21,22 * 19,31 / 41,24 = 9,94  -> (22,93 + 9,94) / 52,8 = 62%
  в Европу:         21,22 * 21,93 / 41,24 = 11,28 -> (34,39 + 11,28) / 70,4 = 65%

Худший случай - отказ зоны и узла в ROW:
  оставшаяся зона:  7 * 7,04 = 49,28 Гбит/с
  перелив:          77,54 - 49,28 = 28,26 Гбит/с
  в US&Canada:      28,26 * 19,31 / 41,24 = 13,23 -> (22,93 + 13,23) / 52,8 = 68%
  в Европу:         28,26 * 21,93 / 41,24 = 15,03 -> (34,39 + 15,03) / 70,4 = 70%
```

Во всех состояниях узлы не превышают порог 80 %, регионы-приёмники остаются не выше 70 %, то есть ниже собственного порога перелива. Перелив состоит из промахов CDN: в ROW их 69 Гбит/с, в Европе 30,6, в US&Canada 20,4 - больше максимального перелива каждого региона (28,26 / 13,27 / 8,85), поэтому API всегда обслуживается в домашнем регионе. Переливаемый файл проходит межрегиональный путь (+100-150 мс) только при первом запросе к edge CDN, дальше он отдаётся из кеша. Одновременный отказ зон в двух регионах не рассматривается: это независимые события.

**Итог:**

| Компонент | US&Canada | Европа | ROW | Итого |
| --- | ---: | ---: | ---: | ---: |
| L4 (N*2) | 2 | 2 | 2 | **6** |
| NGINX рабочих N | 4 | 6 | 13 | 23 |
| NGINX 2 * (⌈N/2⌉+1) | 6 | 8 | 16 | **30** |

По сравнению со схемой 2(N+1) (52 узла) перелив требует на 22 узла (42 %) меньше при той же устойчивости к отказу узла и зоны.

## 5. Логическая схема БД


### 5.1 Логическая схема: основные данные

Объекты (пользователи, доски, пины, медиафайлы) создаются одновременно на многих узлах в трёх регионах. Поэтому единый глобальный автоинкремент не используется: общий счётчик - это точка синхронизации между регионами и единая точка отказа, а независимые счётчики на разных узлах без дополнительной информации дают пересекающиеся значения.

Для `user_id`, `board_id`, `pin_id`, `media_id` используется 64-битный идентификатор (`8 Б`), который:

- выдаётся на том узле, где создаётся объект, без обращения к центральной службе;
- уникален во всей системе;
- в два раза короче бинарного UUID (`16 Б`). Только в `PIN_LIKE` (2,63 трлн строк по два идентификатора) это экономит `2,63 трлн * 2 * 8 Б ≈ 42 ТБ`.

### 5.3 Потоки данных

Создание пина:

```text
клиент --(файл)--> UPLOAD_STAGING              загрузка напрямую в хранилище, минуя сервисы
                       ▼ проверка, превью, вектор
           MEDIA (status: uploading → ready) + MEDIA_FILE
                       ▼
           PIN (+ position на доске)            одна атомарная операция
                       ▼ событие изменения
           PIN_TEXT_INDEX, PIN_VECTOR,          асинхронно, секунды
           BOARD.pin_count
```

Сохранение чужого пина:

```text
PIN оригинала --> новый PIN: board_id      = доска сохраняющего
                             parent_pin_id = оригинал
                             media_id      = тот же файл
              --> событие save --> PIN_STATS.save_count оригинала, USER_INTEREST
```

Лайк:

```text
PIN_LIKE (user_id, pin_id)     источник истины; повторный лайк ничего не меняет
      ▼ событие like - только если строка действительно добавлена
EVENT_STREAM --> PIN_STATS.like_count   пакетом, с отставанием до минуты
             --> USER_INTEREST.score
```

Лента:

```text
USER_INTEREST + признаки из EVENT_STREAM --> ранжирование --> FEED_CACHE (200 pin_id, TTL 30 мин)
FEED_CACHE --> OBJECT_CACHE (пин, автор, доска) --> при промахе: PIN / USER / BOARD
```

Поиск:

```text
текст    --> PIN_TEXT_INDEX --> pin_id --> OBJECT_CACHE
картинка --> вектор (ML-модель) --> PIN_VECTOR: ближайшие соседи --> pin_id --> OBJECT_CACHE
```

Вход:

```text
email / username / id провайдера --> USER --> AUTH_IDENTITY (проверка пароля) --> SESSION (TTL 30 суток)
каждый API-запрос --> SESSION (проверка токена)
```

### 5.7 Консистентность и распределение нагрузки по ключам

Используются три уровня консистентности:

- **строгая** - после подтверждения записи её видят все: уникальность email и username, пароли, отзыв сессии;
- **read-your-writes** - автор сразу видит свои изменения, остальные - через секунды: доски и пины;
- **в конечном счёте** - данные догоняют источник с задержкой от секунд до минут: счётчики, интересы, кеши, поисковые индексы;

Почти все запросы адресованы одному пользователю (его доски, пины, лайки, сессия) или одному пину по id. Перекос создают: вирусные пины (миллионы показов), пользователи с тысячами досок и счётчики популярных пинов. По времени: вечерний пик в каждом регионе по местному времени, часовые пояса сглаживают глобальную кривую; ROW даёт 57,5 % нагрузки.

| Сущность | Консистентность | Распределение нагрузки по ключам |
| --- | --- | --- |
| USER | строгая: username и email уникальны глобально | user_id, равномерно; вход по email и username - отдельный равномерный ключ (хеш) |
| AUTH_IDENTITY | строгая: смена пароля атомарна, сессии отзываются сразу | user_id; вход 6 600/с в пике |
| BOARD | автору - read-your-writes (созданная доска видна сразу), остальным - в конечном счёте, секунды | owner_id; доски и пины пользователя лежат вместе; перекос у пользователей с тысячами досок |
| PIN | создание атомарно с привязкой к доске; автору - read-your-writes; остальным - секунды; правка - чтение-изменение-запись в транзакции | шард доски; сохранение вирусного пина пишет в шард сохраняющего, а не автора - запись распределена; чтение вирусного пина - горячий ключ, его снимают CDN и кеш |
| MEDIA | неизменяема после записи; статусы uploading → ready строго по порядку | media_id; читают все, вирусный файл отдаёт CDN |
| PIN_LIKE | идемпотентна: повторный лайк не меняет состояние; своё состояние пользователь видит сразу, счётчик - в конечном счёте | user_id; запись 27 800/с равномерна; чтение по паре (user_id, pin_id) |
| USER_INTEREST | в конечном счёте, отставание в минуты не влияет на корректность | user_id; записи объединяются по времени |
| CATEGORY | в конечном счёте, обновление за минуты | мала, копия в памяти сервисов |
| PIN_STATS | в конечном счёте, отставание до минуты; инкременты не теряются (события перечитываются из потока), при сбое возможен редкий повторный учёт | pin_id; вирусный пин - горячий ключ, тысячи инкрементов в секунду на одной строке |
| SESSION | строгая внутри региона, отзыв виден сразу; между регионами не реплицируется | token_hash, равномерно; чтение на каждом API-запросе |
| FEED_CACHE | в конечном счёте: лента старше TTL 30 мин не отдаётся | user_id, равномерно |
| BOARD_PINS_CACHE | инвалидация при записи; владелец видит свои изменения сразу | board_id; горячие доски популярных пользователей |
| OBJECT_CACHE | cache-aside; устаревание до TTL допустимо, при изменении объекта ключ удаляется | pin_id; распределение Парето: 1 % пинов даёт 95 % чтений |
| EVENT_STREAM | доставка не реже одного раза; порядок - только внутри пользователя | ключ партиции user_id, равномерно |
| MEDIA_FILE, UPLOAD_STAGING | объект неизменяем; после записи чтение сразу актуально | ключ с хеш-префиксом, равномерно |
| PIN_TEXT_INDEX, PIN_VECTOR | в конечном счёте: пин появляется в поиске через секунды-минуты | хеш pin_id и media_id, равномерно |

### 6.3. Идентификаторы и маршрутизация по шардам

Идентификатор объекта - 64 бита, в которые зашит номер логического шарда [[10]](https://medium.com/pinterest-engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f):

| Биты | Поле | Размер | Назначение |
| --- | --- | --- | --- |
| 63-62 | резерв | 2 бита | на будущее |
| 61-46 | `shard_id` | 16 бит | номер логического шарда, до 65 536 |
| 45-36 | `type` | 10 бит | тип объекта: пользователь, доска, пин, медиа |
| 35-0 | `local_id` | 36 бит | автоинкремент таблицы внутри шарда, до 68,7 млрд |

```text
id       = (shard_id << 46) | (type << 36) | local_id
shard_id = (id >> 46) & 0xFFFF
```

Правила размещения новых объектов:

| Объект | Шард |
| --- | --- |
| пользователь | случайный шард из диапазона своего региона |
| доска | шард владельца |
| пин | шард доски, в том числе сохранённая копия - шард доски сохраняющего |
| медиа | шард загрузившего |

Так все данные одного пользователя (профиль, доски, пины, порядок пинов, счётчики его пинов) лежат на одном шарде: создание пина и обновление доски выполняются одной локальной транзакцией без распределённых.

| Регион | Диапазон `shard_id` | Primary-хостов | Шардов |
| --- | --- | ---: | ---: |
| US&Canada | 0 – 703 | 11 | 704 |
| Европа | 704 – 1 727 | 16 | 1 024 |
| ROW | 1 728 – 4 095 | 37 | 2 368 |
| **Всего** | | **64** | **4 096** |

Каждый хост - ровно 64 шарда, доли регионов 17,2 / 25 / 57,8 % - близко к долям аудитории 17 / 25,5 / 57,5 %. Пользователь живёт в шардах своего региона: его данные лежат рядом с его сервисами.

Маршрут запроса:

```text
pin_id --> shard_id = (pin_id >> 46) & 0xFFFF --> база db_{shard_id}
       --> правило ProxySQL: schema → hostgroup (primary + реплика хоста) --> MySQL
```

### 6.4. Индексы

| Таблица | Индекс | Какой запрос обслуживает | Цена |
| --- | --- | --- | --- |
| `USER` | PK (`user_id`) | профиль, автор на карточке | кластерный, данные в нём же |
| `AUTH_IDENTITY` | PK (`user_id`, `provider`) | способы входа пользователя | кластерный |
| `USER_LOOKUP` | PK (`lookup_type`, `key_hash`) | вход по email, username, id провайдера → `user_id`; уникальность | кластерный |
| `BOARD` | PK (`board_id`); **IDX (`owner_id`, `created_at`)** | список досок пользователя | +120 ГБ |
| `BOARD_PIN` | **PK (`board_id`, `sequence DESC`, `pin_id`)** | страница доски: пины по порядку, листание по ключу, без `OFFSET` | кластерный |
| `PIN` | PK (`pin_id`) | метаданные по id | кластерный |
| `MEDIA` | PK (`media_id`) | файл по id | кластерный |
| `PIN_STATS` | PK (`pin_id`) | счётчики пина | кластерный |
| `PIN_LIKE` (TiDB) | PK (`user_id`, `pin_id`); **IDX (`user_id`, `created_at DESC`, `pin_id`)** | «лайкнул ли» и список лайков по времени | +52,6 ТБ |
| `USER_INTEREST` (TiDB) | PK (`user_id`, `category_id`) | все интересы пользователя одним диапазоном | кластерный |

В InnoDB первичный ключ - кластерный: строки физически упорядочены по нему, поэтому чтение по PK - один проход по B+-дереву, а вторичный индекс хранит значение PK и требует второго поиска. Отсюда выбор ключей: `BOARD_PIN` упорядочен так, как страница доски читается, а `PIN_LIKE` начинается с `user_id`, чтобы все лайки пользователя лежали рядом.

Индексы, которые **сознательно не создаются**:
- `PIN (parent_pin_id)` - 300 млрд × 16 Б = 4,8 ТБ; запрос «кто сохранил этот пин» в MVP не нужен;
- `PIN (author_id)` - вкладка «Создано» вне MVP, пины пользователя доступны через его доски;
- `PIN (media_id)` - визуальный поиск получает `pin_id` прямо из ANN-индекса;
- `MEDIA (checksum)` уникальный - 12 ТБ, и уникальность невозможна между шардами;
- `PIN (category_id)` - выбор по теме выполняет поисковый индекс.

### 6.5. Денормализация

| Что | Где | Зачем | Цена |
| --- | --- | --- | --- |
| `media_key`, ширина, высота | в `PIN` из `MEDIA` | чтение `MEDIA` при каждом показе (370 000/с, 1,1 млн в пике) исчезает из пути ленты | +44 Б на пин = 13,2 ТБ (+14,6 % к PIN); аномалий нет - медиафайл неизменяем |
| Упорядоченный список пинов | `BOARD_PIN` отдельно от `PIN` (вместо `PIN.position`) | страница доски читает 20-байтные строки и затем объекты по id (прикладной JOIN); порядок хранится в ключе | 6,0 ТБ; запись пина - две строки в одной транзакции |
| Счётчики | `PIN_STATS` отдельно от `PIN` + пакетная запись | строка `PIN` в 342 Б не перезаписывается и не блокируется при тысячах инкрементов в секунду; пакет раз в 10 с снижает запись с 93 000 до 9 300 в секунду в пике | 6,0 ТБ; счётчик отстаёт до 10–60 с |
| `pin_count`, `cover_pin_id` | в `BOARD` | заголовок доски без подсчёта пинов | обновляются асинхронно, расхождение временное |
| Лайки в двух порядках | `PIN_LIKE`: ключ и вторичный индекс | проверка «лайкнул ли» по паре и список по времени | +52,6 ТБ |
| `pin_id` оригинала | в `PIN_VECTOR` | визуальный поиск возвращает пин без индекса `PIN (media_id)` | +8 Б на вектор |
| Поиск шарда по неидентификатору | `USER_LOOKUP` | email, username и id провайдера не содержат номера шарда | 42,5 ГБ |

Не денормализуются изменяемые поля: имя автора и название доски **не копируются** в `PIN`. Ссылки хранятся по неизменяемым id, имена подставляет сервис при сборке ответа из кеша [[10]](https://medium.com/pinterest-engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f): иначе смена username потребовала бы обновить миллиарды строк.

**Как работают счётчики.** Лайки приходят в Kafka из TiCDC, сохранения - из Debezium, клики - от приложения. Потребитель-счётчик:
1. читает события пачкой и суммирует их по `pin_id` в памяти за окно 10 с;
2. сразу прибавляет суммы в Redis (`HINCRBY pinstats:{pin_id}`) - это «свежая» часть счётчика для показа;
3. в конце окна одним `UPDATE` на шард прибавляет суммы в `PIN_STATS` (MySQL);
4. вычитает перенесённые суммы из Redis;
5. только после этого фиксирует смещение в Kafka.

Показываемое значение = `PIN_STATS` + дельта из Redis. Если потребитель упал до шага 5, события будут прочитаны повторно - возможен редкий двойной учёт (доставка не реже одного раза), но инкременты не теряются. Если пропал Redis, теряется только отображение последних секунд: источник - MySQL и Kafka.

| ProxySQL | правила запросов: schema → hostgroup; запись и `SELECT ... FOR UPDATE` - в primary, остальное чтение в реплику [[22]](https://proxysql.com/documentation/) | разделение чтения и записи, пул соединений |
| ZooKeeper | Apache Curator | хранение карты «шард → хост», синхронизация её в ProxySQL |
| TiDB | тот же MySQL-драйвер (протокол совместим); L4-балансировщик перед `tidb-server` | SQL-доступ к `PIN_LIKE` и `USER_INTEREST` |
| Redis | Lettuce (поддержка Redis Cluster, асинхронный) | сессии, лента, списки, дельты счётчиков |
| Memcached | клиент → mcrouter [[29]](https://github.com/facebook/mcrouter) | consistent hashing, пулы |
| Kafka | Apache Kafka Java client: `acks=all`, `enable.idempotence=true`, пакетная отправка | события; группы потребителей: счётчики, интересы, признаки ранжирования, индексатор, инвалидация, sink |
| S3 | AWS SDK: multipart upload, presigned URL | клиент загружает файл напрямую в S3, минуя сервисы |
| Поиск | клиент OpenSearch; gRPC к ANN-сервису | текстовый и визуальный поиск |
| CDC | Debezium [[25]](https://debezium.io/documentation/) (binlog MySQL → Kafka), TiCDC (TiDB → Kafka) | индексы, инвалидация кешей, счётчики |
| Аналитика | ежесуточные снимки MySQL и TiDB в S3 | озеро данных для обучения моделей; выгрузка снимка в объектное хранилище была требованием Pinterest при выборе хранилища [[19]](https://medium.com/pinterest-engineering/tidb-adoption-at-pinterest-1130ab787a10), дампы MySQL в S3 - в [[10]](https://medium.com/pinterest-engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f) |

### 6.7. Балансировка запросов и мультиплексирование подключений

Нагрузка на СУБД после кешей (пик). Кеши снимают: Memcached - 95 % чтений `PIN`, `USER`, `BOARD`; Redis - 90 % чтений списка доски и интересов; пакетная запись - 90 % записи `PIN_STATS`.

| Таблица | Чтение | Запись |
| --- | --- | --- |
| `PIN` | 55 000 | 7 950 |
| `BOARD_PIN` | 1 665 | 7 950 |
| `USER` | 3 382 | 30 |
| `BOARD` | 1 208 | 42 |
| `AUTH_IDENTITY` | 6 600 | 15 |
| `USER_LOOKUP` | 6 600 | 30 |
| `MEDIA` | 0 (денормализация) | 420 |
| `PIN_STATS` | 2 775 | 9 300 |
| **Итого MySQL** | **77 230** | **25 737** |
| `PIN_LIKE` (TiDB) | 55 500 | 83 000 строк |
| `USER_INTEREST` (TiDB) | 9 825 | 18 180 |
| **Итого TiDB** | **65 325** | **101 180** |

**MySQL.** Весь трафик к MySQL идёт через ProxySQL (два узла на ДЦ, схема N×2 из раздела 4). ProxySQL выбирает группу хостов по имени базы `db_{shard_id}` и по типу запроса:
- запись и чтение с блокировкой - в primary шарда;
- обычное чтение - в полусинхронную реплику, если её отставание меньше `max_replication_lag` (1 с), иначе в primary;
- чтение автором своих только что изменённых объектов (read-your-writes) сервис помечает, и оно идёт в primary.

На один хост в пике: `25 737 / 64 ≈ 402` записи/с на primary и `77 230 / 64 ≈ 1 207` чтений/с на реплику. Региональный ДЦ ROW получает 57,5 % от 103 000 QPS ≈ **59 200 QPS** (44 400 чтений + 14 800 записей); один узел ProxySQL должен выдержать это в одиночку: принято требование ≥ 60 000 QPS на узел, подтверждается нагрузочным тестом.

| Параметр | Значение |
| --- | --- |
| Подов сервисов | 492 = 245 562 / 500 RPS на под |
| Пул подов | 4 соединения на каждый из 64 хостов |
| Без прокси | на каждом хосте 492 × 4 = **1 968** соединений |
| Нагрузка на хост | 103 000 / 64 = 1 609 QPS |
| Одновременных запросов (закон Литтла L = λ × W, W = 2 мс) | 1 609 × 0,002 ≈ 3,2 |
| С ProxySQL | пул 32 соединения на хост (запас в 10 раз) → в **61** раз меньше |

Мультиплексирование: ProxySQL держит небольшой пул постоянных соединений к MySQL и отдаёт соединение клиентскому запросу только на время выполнения запроса, а не на всё время жизни клиентского соединения. Каждое соединение MySQL - это поток и буферы на сервере, поэтому 1 968 простаивающих соединений тратят память, которая нужна под кеш страниц InnoDB.

**TiDB.** Подключения принимают серверы `tidb-server` без состояния за L4-балансировщиком; распределение по данным выполняет сам кластер (PD).
**Redis Cluster.** Клиент знает слот ключа (`CRC16(key) mod 16384`) и обращается сразу к нужному шарду; чтение - с master, чтобы не получить устаревшую сессию.
**Memcached.** mcrouter раскладывает ключи по узлам consistent hashing: при добавлении узла переезжает только `1/N` ключей.
**Kafka.** Продюсер выбирает партицию по ключу, события одного пользователя идут по порядку; группа потребителей делит партиции между экземплярами.

### 6.8. Схема резервного копирования

| Хранилище | Метод | Частота и хранение | RPO | RTO |
| --- | --- | --- | --- | --- |
| MySQL (основной и `USER_LOOKUP`) | полный физический снимок реплики (Percona XtraBackup [[28]](https://docs.percona.com/percona-xtrabackup/)) в S3 + непрерывная выгрузка binlog в S3 для восстановления на момент времени | снимок раз в сутки, 14 суток; месячные снимки 12 месяцев; binlog 14 суток | до 5 минут (binlog) | отказ хоста: полусинхронная реплика становится primary автоматически (Orchestrator [[27]](https://github.com/openark/orchestrator)), около минуты; потеря всех копий: восстановление хоста 2,8 ТБ ≈ 37 мин передачи по 10 Гбит/с + проигрывание binlog, 1,5–2 ч |
| TiDB | BR [[26]](https://docs.pingcap.com/tidb/stable/backup-and-restore-overview): полный снимок + журнал изменений в S3 | снимок раз в неделю, журнал непрерывно, 14 суток | до 5 минут | потеря зоны: ноль, 3 реплики Raft; потеря региона: часы-сутки (оценка), лайки и интересы вторичны |
| Redis: сессии | реплика в другой зоне; RDB-снимок раз в час для быстрого прогрева | снимок 24 часа | потеря сессий = повторный вход | минуты |
| Redis: ленты, списки, дельты счётчиков | не копируются: пересчитываются из источника (MySQL, Kafka) | - | - | минуты (прогрев) |
| Memcached | не копируется | - | - | прогрев кеша |
| Kafka | RF = 3, `acks=all`; sink в S3 для озера данных | хранение 3 суток в Kafka, в озере - бессрочно | 0 | минуты (перевыбор лидера) |
| S3: `MEDIA_FILE` | версионирование + репликация оригиналов в другой регион; долговечность 99 % | бессрочно | минуты (репликация) | переключение чтения на бакет-реплику |
| S3: `UPLOAD_STAGING` | не копируется, правило удаления через 24 ч | 24 часа | - | загрузку повторяет клиент |
| OpenSearch, ANN | производные: снимок в S3 раз в сутки; при потере - пересборка из MySQL и S3 через CDC | 7 суток | не применимо | часы (пересборка) |

Принцип 3-2-1 для критичных данных (MySQL, оригиналы файлов): три копии (primary, реплика, снимок), два типа носителей (диск хоста и S3), одна копия в другом регионе. Бакет с резервными копиями защищён Object Lock: снимок нельзя удалить ни ошибкой, ни атакой до окончания срока хранения. Восстановление проверяется раз в месяц на тестовом хосте: бэкап без проверки восстановления не считается бэкапом. В [[10]](https://medium.com/pinterest-engineering/sharding-pinterest-how-we-scaled-our-mysql-fleet-3f341e96ca6f) реплика также служила для резервного копирования и выгрузки в S3, но повышение реплики выполняли вручную скриптами; здесь выбрано автоматическое - это проектное решение.
